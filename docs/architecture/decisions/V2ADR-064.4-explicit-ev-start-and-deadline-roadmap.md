# V2ADR-064.4 - Explicit EV start and deadline planning

Status: direct-start slice approved by Alex on 2026-10-17; locally implemented.
The agreed subsequent HEMS scheduling slices are designed here, not implemented.
Baseline: main 542de25f4f0aa29303c1835cbe50d2f13f66ec4a, HEMS dev.299.

## User contract

The user starts a session to attest that the car is physically plugged in.
BMW cannot detect the cable while the Shelly is off. Neither BMW plug status nor
a preliminary charging measurement is an admission requirement for direct start.
The existing automatic recognition path remains compatible.

Energy Devices owns the selected plug and durable session. HEMS remains the sole
economic planner. No battery command or tariff selection is added to the producer.
This extends V2ADR-064.3 only for explicit immediate start; the existing future
manual placement retains its resume-test requirement.

## Implemented first slice

The user saves a power/duration profile once and presses Nu laden. The profile is
persisted against the configured meter/switch pair; changing that pair clears it.
An open session blocks another start. Updating the profile does not rewrite an
existing session. The API stores intent; the normal runtime tick dispatches only
to its configured switch. No measurement is fabricated at session creation.

Direct start authorizes that session's switch execution without the old probe or
resume-test gate. Unknown switch state does not authorize an on command. Existing
ten-second command retries, cancellation, hard stop, and durable restart handling
are retained. Actual measured power confirms charging. After 120 seconds with the
plug observed on but no fresh charging power, the UI reports charging_not_started;
unavailable measurements are reported separately and never prove completion.
Manual off is respected even before the first charging sample. Explicit resume
can restart within the original interval. Natural completion still requires actual
charging followed by the existing five-minute available low-power period.

The duration is a user estimate and maximum run time, not a deadline-based promise
of 100% SOC. Missing measurements leave energy incomplete. This slice does not
configure BMW sensors or infer remaining battery capacity.

## HEMS compatibility and next slices

The current energy-device-session-demand:v1 consumer accepts one confirmed window
with duration <=24 hours. It does not choose charging slots. It separates measured
EV demand from household history under existing evidence/coverage rules. A direct
session uses that same interface; HEMS production code is unchanged in this slice.

A Saturday-to-Monday request cannot be represented by extending that one window:
availability, required charging duration, and deadline are different quantities.
The next slice needs a separate versioned request containing session ID/revision,
available_from, ready_by, remaining grid-side Wh, fixed W, evidence source/time,
and charge target. Unknown SOC must permit explicit kWh or duration input. BMW's
original measurement timestamp must remain distinct from a refreshed HA/MQTT value.

HEMS must evaluate bounded EV placement candidates through its canonical planning
and evaluation chain, preserving active battery commitments and residual-load
accounting. Energy Devices must not implement a parallel price-ranking algorithm.
Initial output is advisory: slots, required versus scheduled energy, known price
coverage, feasibility, costs and effect on the battery plan. Unknown future prices
must remain unknown; a provisional schedule is not a proven global optimum.

Before automatic execution, define and test a schedule contract with session ID,
request revision, schedule revision, input evidence and ordered non-overlapping
slots. Reject old, cancelled or mismatched sessions. Revisions may alter future
slots; active-block continuity and minimum on/off times need explicit rules.
Cancellation must invalidate every outstanding schedule. Pauses retain identity
even when BMW reports disconnected because the plug is intentionally off.

An eventual local latest-start guard uses remaining duration plus a declared
margin, never independent tariff optimization. Its activation must be reported
to HEMS as actual demand. Unachievable deadlines must be visible, not represented
as completed charging. This guard is not present in the direct-start slice.

## Verification gates for scheduling

- Partial prices across Saturday/Monday and local timezone/DST transitions.
- Insufficient duration, target changes, stale or estimated BMW SOC.
- Same-session idempotence, cancellation versus dispatch, restart between slots.
- No double counting of historic/actual/planned EV load.
- Preserved committed battery routes and canonical run/snapshot lineage.
- End-time guard behavior without usable HEMS output and visible infeasibility.
- Real Shelly switching and BMW resumption after installation.

Release and installation are separate from local implementation. Existing HEMS
dev.299 and live Home Assistant configuration are not modified by this work.
