## Decisions

### Zendure v1 strategy

PicoT v1 will build on the existing @gielz integration as the primary Zendure execution layer. A first-party PicoT ZenSDK adapter is deferred until the Core and v1 are stable, unless a proven structural limitation requires it earlier.

### Execution Primitives

The Core does not know vendor modes. It expresses generic desired energy behaviour:

- `STANDBY`
- `STOP_ALL`
- `BALANCE_BIDIRECTIONAL`
- `BALANCE_CHARGE_ONLY`
- `BALANCE_DISCHARGE_ONLY`
- `CHARGE_AT_POWER`
- `DISCHARGE_AT_POWER`

Device Adapters translate these primitives to vendor-specific commands.

### Execution Plan Architecture

The Planner produces an immutable, time-bound Execution Plan instead of direct commands. Each due segment is validated against current reality before execution.

Conflicting User Rules are not silently resolved. All conflicting rules are automatically disabled without changing their content, the conflict is logged, push and dashboard notifications are issued, and the standard PicoT Planner replans with the remaining valid rules.

Official status: `USER_RULE_CONFLICT_AUTO_DISABLED`.

### Planning Decision Pipeline

PicoT evaluates complete energy paths rather than isolated actions.

- Nominal rolling planning horizon: 36 hours.
- Replanning is event-driven by material knowledge changes.
- Inputs carry explicit confidence.
- Candidates are evaluated for future demand coverage and recoverability.
- Confidence, constraints, recoverability and dominance reduce the Candidate search space before full simulation.

### User Objective Model

Users configure personal priorities rather than technical battery modes. Independent objectives may include cost, battery longevity, self-consumption, trading, reserve and sustainability.

An Objective Mapping Layer separates the user-facing sliders and wizard from internal Planner weights. The mapping may use larger or non-linear internal steps so meaningful user changes have noticeable influence while remaining transparent and deterministic.
