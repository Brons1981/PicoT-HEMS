## Decisions

### Energy Profile Model

User Rules and Energy Profiles remain separate Core concepts.

A User Rule defines when, under which conditions and which action is executed. In Expert mode it may optionally contain a user-declared Planning Hint describing expected power, duration and energy.

Learning may evolve this into a Managed Energy Profile, but may never modify the IF/AND/OR/THEN logic or the external action target.

External Home Assistant automations and Homey flows remain black boxes. PicoT only triggers explicitly selected actions and never assumes their internal energy behaviour.

### Dual User Input Model

Where useful, PicoT offers:

- Simple mode for guided visual configuration;
- Expert mode for more precise and expressive configuration.

Both modes produce the same validated internal model. Expert mode never receives additional authority and cannot bypass Safety, hard constraints, validation, conflict handling or the Execution Pipeline.

### Layered Diagnostic Isolation

Diagnosis is non-destructive and proceeds per layer using temporary fallbacks.

Examples include bypassing User Rules, Expert configuration, Planning Hints, learned Energy Profiles, external actions or advanced Planner optimisation.

Original configuration remains unchanged and is restored after diagnosis. Baseline functionality and essential source data remain available.

### Progressive Complexity

The default PicoT experience remains simple. Additional complexity is shown only after explicit opt-in.

New functionality should extend existing Core models and reuse the same Planner, Explainability, Diagnostics and Execution Pipeline instead of creating parallel systems.

### Opportunity Engine

The Opportunity Engine derives objective, evidence-backed opportunities and constraints from the Planning Input Set. It does not select devices, assign power, create Candidates or make plans.

The complete decision chain is:

1. Opportunity Engine;
2. Candidate Engine;
3. Evaluation Engine;
4. Execution Plan;
5. Execution Engine.

Each stage deterministically reduces the solution space or converts an already-selected result without introducing a new energy decision.

### Candidate Engine

A Candidate is a complete household energy path over the planning horizon.

The Candidate Engine uses:

- hard reduction for impossible scenarios;
- controlled branching for meaningful alternatives;
- Candidate Families for sequential, parallel, priority-first, PV-first and related paths;
- User Objectives for strategic direction;
- the Optimisation Profile for search breadth;
- safe dominance removal only where one Candidate is objectively nowhere better.

### Planner Strategy Model

User Objectives and the Optimisation Profile are a cross-cutting strategic model beside the Planning Pipeline, not a separate layer.

User Objectives describe what the user wants to achieve. User Rules define explicit constraints.

The strategy is immutable during a Planner Run and may only be changed by explicit user action.

A Planning Preview can calculate and compare a proposed strategy before activation. It is a forecast based on current information, not a guarantee.

### Evaluation Engine

Candidates are compared deterministically per strategic objective. PicoT does not rely on an opaque aggregate score.

Tie-break order follows descending User Objective priority, then confidence, recoverability, execution simplicity, expected switching count and finally stable Candidate identifier order.

### Execution commitments

An active Execution Plan is a stable commitment with live monitoring.

New Planner Runs optimise around active commitments. Only technically and explicitly flexible parts may change.

The complete control chain determines interruptibility, power adjustability, resume behaviour and anti-flipper boundaries.

Dynamic Power Allocation remains active around commitments and may steer battery charge, discharge or standby, PV surplus, grid import/export and flexible loads.

No separate Execution Orchestrator layer is introduced; coordination remains inside the existing Execution Engine.

### Runtime Resource Governance

PicoT governs CPU, memory, storage, Planner duration, queues and concurrent work through measured baselines, pressure states and graceful degradation.

States are:

- `NORMAL`;
- `TRANSIENT_PRESSURE`;
- `SUSTAINED_PRESSURE`.

Short peaks do not cause permanent degradation. Sustained pressure causes controlled scaling back, hysteresis, logging and a user-visible notification.

Safety, hard limits, active commitments and critical monitoring always keep priority over extended optimisation, Learning and non-critical dashboard analysis.

A coloured Runtime Health Indicator on the dashboard combines CPU, available memory, Planner duration and pressure state, and directs the user toward the likely cause.

Only one full Planner Run may be active. There is always a fixed five-second stabilisation interval from the end of one Planner Run to the start of the next.

Events during this interval only set `REPLAN_REQUIRED = true`. Every new Planner Run starts from a completely fresh atomic Planning Input Snapshot.

Hardware qualification is based on measured resource profiles and reproducible benchmarks, not hardware brand assumptions.

### Household Power Capacity Management

The physical phase distribution is a fixed system constraint. PicoT cannot move devices or sources between phases.

PicoT may monitor, plan, constrain, explain and advise within the existing installation.

`Net Balance` becomes a User Objective. It may influence optimisation preference, but can never disable hard phase-current, voltage, fuse or hardware limits.

PicoT always explains when an action is denied, reduced, stopped or deferred because of a hard limit.

Where measurements permit, PicoT monitors phase voltage and may correlate high voltage with PV inverter curtailment or shutdown.

Long-term evidence may lead to Installation Insight, such as advising a user to ask a qualified installer whether an EV charger or PV inverter would perform better on another phase. PicoT never performs or guarantees such physical changes.

### Future PEP

A high-priority future PEP was added for phase-load and voltage monitoring. It covers per-phase current, power, voltage, phase loss, imbalance, high-voltage PV shutdown insight and installer-facing evidence.

## Implemented Core contracts and engines

### ADR-030 — Energy Path and Capability Snapshot Contract

Implemented immutable, vendor-independent capability and path records, including:

- `ExecutionPrimitive`;
- `LogicalCapabilitySnapshot`;
- `CapabilitySnapshotSet`;
- `PathSegment`;
- `SocConstraint`;
- `ProjectedEnergyState`;
- `EnergyPath`.

Validation covers chronology, timezone awareness, capability references, mapping versions, power requirements, SoC bounds, ordering and per-scope overlap.

### ADR-031 — Candidate Scenario Construction Contract

Implemented the first deterministic Candidate Engine slice:

- a baseline Candidate and Energy Path;
- a PV-first storage Candidate when supported;
- explicit logical capability roles;
- filtering on availability, health, primitive, flow direction and power limits;
- explicit exclusions when a scenario cannot be constructed;
- deterministic identifiers and ordering.

`CandidateSet` now contains Candidates, their Energy Paths and exclusions atomically. Every Candidate references exactly one included Energy Path.

### ADR-032 — Candidate Evaluation Contract

Implemented immutable evaluation input and output records:

- `ObjectiveOutcome`;
- `CandidateOutcome`;
- `CandidateOutcomeSet`;
- `EvaluationRecord`;
- `EvaluationResult`.

The Evaluation Engine now:

- validates atomic Candidate and Outcome inputs;
- excludes invalid Candidates while preserving their reasons;
- compares objectives in Planner Strategy order;
- applies deterministic confidence, recoverability, complexity, switching-count and Candidate-ID tie-breaks;
- selects one existing Candidate and Energy Path;
- returns explicit `NO_VALID_CANDIDATE` when no valid option exists.

### ADR-033 — Winning Energy Path to Execution Plans

Implemented immutable execution-plan contracts and deterministic conversion:

- `ExecutionPlanSegment`;
- `ExecutionPlan`;
- `ExecutionPlanSet`;
- `ExecutionPlanBuilder`.

One Winning Energy Path is converted without reinterpretation into one scope-specific Execution Plan per `execution_scope_id`. Baseline paths without controllable actions produce a valid empty Plan Set.

### Execution Engine v1

Implemented the first vendor-independent Execution Engine slice:

- selection of due Execution Plan segments;
- validation of snapshot and capability mapping versions;
- validation of capability scope, availability, health and primitive support;
- deterministic `ExecutionPrimitiveRequest` and `ExecutionRecord` identifiers;
- `REPLAN_REQUIRED` for missing or unusable capabilities;
- no vendor commands, Device Adapters, retries or acknowledgements yet.

The implementation closes the PicoT Core v0 pipeline through generic Execution Primitive requests.

## PicoT Core v0 pipeline milestone

The complete implemented pipeline is now:

```text
PlanningInputSnapshot
→ Opportunity Engine
→ OpportunitySet
→ Candidate Engine
→ CandidateSet + EnergyPaths
→ Evaluation Engine
→ Winning Candidate + Winning Energy Path
→ Execution Plan Builder
→ ExecutionPlanSet
→ Execution Engine
→ ExecutionPrimitiveRequest
```

The pipeline is:

- deterministic;
- immutable;
- explainable;
- vendor-independent;
- ADR-driven;
- covered by Ruff, Mypy and Pytest in GitHub Actions.

No extra orchestration layer was introduced.
