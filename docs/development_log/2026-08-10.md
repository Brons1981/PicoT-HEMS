## Replanning design milestone

PEP-RP-001 defines the accepted direction for Plan Deviation & Replanning.

Core decisions:

- a detected deviation triggers a plan review, not an immediate control action;
- PicoT first checks whether the current plan is still feasible;
- no-action is a valid and explainable planner outcome;
- PV, P1/grid, load, battery behaviour and SoC trajectory may all contribute to later replanning phases;
- hysteresis / anti-flip behaviour is required to avoid reacting to short cloud events;
- discretionary battery discharge must have a feasible recovery/recharge plan;
- discharge is only justified when the price spread remains worthwhile after recharge cost, RTE losses, battery wear and a minimum decision margin.

## Phase 1 Plan Review implementation

The first implementation remains deliberately observation-only.

When `pv_deviation_replan_candidate` becomes true, PicoT creates a deterministic Plan Review record with:

- trigger;
- rolling PV deviation;
- P1/grid import/export evidence;
- battery SoC and charge/discharge evidence;
- feasibility scope `phase1_observation_only`;
- outcome `current_plan_still_feasible` where applicable;
- action `keep_current_plan`;
- `control_change_allowed: false`.

Phase 1 therefore proves the review chain without permitting control changes.

## Live PV deviation test

A live Home Assistant test was performed by temporarily disabling the PV inverter.

Observed behaviour:

1. GoodWe actual PV dropped while Solcast expected PV remained available.
2. Rolling PV deviation crossed the configured 25% threshold.
3. `replan_candidate` became true.
4. Plan Review ran and retained the current plan.
5. No control change was authorised.
6. After PV returned and the rolling window recovered, the evaluator returned to `within_tolerance` and `replan_candidate` became false.

This confirmed the intended anti-flip behaviour: PicoT did not immediately change the plan because of a short disturbance.

Zendure mode changes observed during the test were not caused by PicoT Plan Review; the external Zendure integration / SoC behaviour remained responsible for those transitions.

## Planner event timeline

A deterministic semantic timeline was added for Home Assistant Recorder.

Supported transitions:

- `replan_start`;
- `plan_review`;
- `plan_kept`;
- `replan_required`;
- `replan_cleared`.

The timeline is stateful and deduplicated so unchanged 5-second telemetry samples do not create repeated events.

`sensor.picot_planner_timeline` is created at add-on startup with state `idle`. After startup it changes only on real semantic planner events. `idle` is initialization only and is not logged as a planner decision.
