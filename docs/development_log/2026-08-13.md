# Development Log — 2026-08-13

## Purpose

This log records the current PicoT HEMS recovery trajectory back to the accepted ADR architecture. It exists to prevent future implementation work from treating currently running legacy or transitional code as architectural truth.

This document is **contextual and non-normative**. Accepted ADRs remain authoritative. If implementation and an accepted ADR differ, the ADR wins. Accepted ADRs are not rewritten to fit current code. If an accepted ADR is incomplete or a real conflict exists, PicoT creates a new ADR. If implementation cannot be made to follow the architecture without a workaround, implementation stops and the design returns to the drawing board.

## Why this recovery work is necessary

Earlier PicoT development moved too quickly from planner output toward live Home Assistant/Zendure behaviour and, in places, implemented direct runtime shortcuts before the complete ADR execution chain was wired end-to-end.

Those shortcuts helped validate live evidence and device behaviour, but they must not become permanent architecture merely because they currently work or appear in the add-on configuration.

The present objective is therefore not to extend the old path. It is to reconnect the live runtime to the architecture already accepted in the ADR set.

## Control interface remains @gielz / Zendure mode selection

The current Home Assistant configuration contains the @gielz Zendure mode selector, for example:

`input_select.zendure_2400_ac_modus_selecteren`

That is intentional as the present device-facing control interface.

The architectural correction is **not** to replace this with an unrelated direct-control path. PicoT Core remains vendor-independent and produces generic Execution Primitives. The adapter boundary translates those primitives into the existing @gielz/Zendure control semantics, including use of the mode selector where appropriate.

Therefore:

- planner logic must not contain Zendure mode names;
- candidate identifiers must not be interpreted as vendor commands;
- vendor-specific mode names remain confined to the adapter/runtime boundary;
- the existing @gielz integration remains the current device-facing mechanism unless a future accepted ADR deliberately changes that architecture.

## Accepted execution architecture to restore

The intended chain is already defined by accepted ADRs:

1. Planning Input Snapshot and canonical evidence
2. Opportunity detection
3. Candidate generation
4. Evaluation and Winning Candidate / Winning Energy Path
5. Winning Energy Path conversion to `ExecutionPlanSet`
6. Execution Engine validation of due segments
7. `ExecutionPrimitiveRequest`
8. Device Adapter translation
9. Home Assistant / @gielz / Zendure command dispatch
10. Runtime observation, execution evidence and replanning where required

Relevant accepted ADRs include at least:

- ADR-015 — Execution Primitive Architecture
- ADR-016 — Execution Plan Architecture
- ADR-027 — Execution Plan Commitment and Dynamic Power Allocation
- ADR-033 — Winning Energy Path to Execution Plans
- ADR-034 — Runtime Monitor Material Change Replanning Contract
- ADR-035 — Home Assistant Adapter and Controlled Dispatch Contract
- ADR-037 — Household Energy Requirement / Storage Reserve / Grid Use
- ADR-042 — Regime-aware Closed-loop Flow Validation
- ADR-043 — Storage Requirement Temporal Semantics
- ADR-044 — Timed Storage Acquisition Candidate Selection
- ADR-045 — Canonical PV Deviation Planner Evidence

## Work completed during the recovery trajectory

During the recent recovery work the evidence and planner side has been rebuilt around the accepted architecture instead of the older shortcut behaviour.

The live pipeline now includes, among other things:

- canonical price evidence from the live Planning Input Snapshot;
- canonical quarter-hour PV/load normalisation;
- actual PV energy integrated on canonical quarter boundaries;
- canonical PV forecast-versus-actual deviation evidence;
- ADR-034-compatible replan evidence from material PV deviation;
- projected household energy balance;
- effective storage limits;
- storage requirement and protected interval semantics;
- PV-only feasibility;
- technical recoverability;
- exact timed storage acquisition intervals;
- Candidate generation;
- Evaluation and Winning Candidate selection;
- closed-loop flow observation and regime validation.

As of the current state, the live observer snapshot can reach the evaluation stage and expose a selected winner.

## Current runtime gap

The main remaining architectural gap is between live Evaluation and the existing Execution architecture.

The current live ADR-037 readiness path runs the real planner pipeline and obtains a real planning result, including the Evaluation Result and Winning Energy Path, but then reduces that result to dashboard/log fields. The rich domain object is not yet carried forward into `ExecutionPlanBuilder` and `ExecutionEngine`.

Separately, the transitional `LiveModeControl` path can infer certain @gielz/Zendure modes directly from patterns in a winning candidate identifier. That behaviour is a historical shortcut and must **not** be expanded into the permanent execution route.

In particular, future timed charging must not be implemented as:

`candidate_id -> vendor mode`

The restored architecture must be:

`EvaluationResult -> ExecutionPlanSet -> ExecutionEngine -> ExecutionPrimitiveRequest -> adapter -> @gielz/Zendure command`

## ADR-044 timed acquisition status

ADR-044 can already produce timed Energy Path segments when additional acquisition is required. Those segments contain the generic execution intent, including timing and requested power where applicable.

The next task is therefore not to invent another candidate type or bypass execution validation. The next task is to carry the evaluated winner through the accepted execution contracts.

## Rules for all work from this point

The following rules apply to the recovery work:

- Accepted ADRs are frozen architectural records.
- Do not edit an accepted ADR merely to match existing code.
- When an ADR is genuinely incomplete or conflicts with another accepted ADR, create a new ADR describing the missing decision or resolution.
- Do not implement architectural policy hidden inside runtime conditionals, candidate-ID parsing, adapter exceptions or one-off device hacks.
- Do not treat existing live configuration or legacy runtime code as architectural authority.
- Do not create a workaround just to make live control happen sooner.
- Keep dry-run/observer operation as the safe default while restoring the execution chain.
- Before enabling live control, prove the complete traceability chain from planning evidence to execution request and adapter dispatch.
- If the accepted architecture cannot be implemented cleanly, stop implementation and return to design review.

## Immediate next step

Audit and wire the live runtime so that the real ADR-037 `EvaluationResult` is preserved after evaluation and is handed directly to the existing ADR-033 `ExecutionPlanBuilder`.

From there, continue through the existing `ExecutionEngine` and adapter contracts rather than extending `LiveModeControl` candidate-ID shortcuts.

Only after that path is complete and tested in dry-run should live dispatch be considered.

## Important interpretation note

A currently working path is not automatically the correct PicoT path.

During this recovery phase, implementation must be judged against accepted ADRs first. Existing code is evidence of current behaviour, not proof of intended architecture.
