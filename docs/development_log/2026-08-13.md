# Development Log — 2026-08-13

## Purpose

This log records the current PicoT HEMS recovery trajectory back to the accepted ADR architecture. It exists to prevent future implementation work from treating currently running legacy or transitional code as architectural truth.

This document is **contextual and non-normative**. Accepted ADRs remain authoritative. If implementation and an accepted ADR differ, the ADR wins. Accepted ADRs are not rewritten to fit current code. If an accepted ADR is incomplete or a real conflict exists, PicoT creates a new ADR. If implementation cannot be made to follow the architecture without a workaround, implementation stops and the design returns to the drawing board.

## Why this recovery work is necessary

Earlier PicoT development moved too quickly from planner output toward live Home Assistant/Zendure behaviour and, in places, implemented direct runtime shortcuts before the complete ADR execution chain was wired end-to-end.

Those shortcuts helped validate live evidence and device behaviour, but they must not become permanent architecture merely because they currently work or appear in the add-on configuration.

The present objective is therefore not to extend the old path. It is to reconnect the live runtime to the architecture already accepted in the ADR set.

## Control interface remains @gielz / Zendure mode selection

The current Home Assistant configuration contains the @gielz Zendure mode selector, for example:

`input_select.zendure_2400_ac_modus_selecteren`

That is intentional as the present device-facing control interface.

The architectural correction is **not** to replace this with an unrelated direct-control path. PicoT Core remains vendor-independent and produces generic Execution Primitives. The adapter boundary translates those primitives into the existing @gielz/Zendure control semantics, including use of the mode selector where appropriate.

Therefore:

- planner logic must not contain Zendure mode names;
- candidate identifiers must not be interpreted as vendor commands in the final architecture;
- vendor-specific mode names remain confined to the adapter/device-facing boundary;
- the existing @gielz integration remains the current device-facing mechanism unless a future accepted ADR deliberately changes that architecture.

## Accepted execution architecture to restore

The intended chain is already defined by accepted ADRs:

1. Planning Input Snapshot and canonical evidence
2. Opportunity detection
3. Candidate generation
4. Evaluation and Winning Candidate / Winning Energy Path
5. Winning Energy Path conversion to `ExecutionPlanSet`
6. Execution Engine validation of due segments
7. `ExecutionPrimitiveRequest`
8. Device Adapter translation
9. Home Assistant / @gielz / Zendure command dispatch
10. Runtime observation, execution evidence and replanning where required

## Historical correction: role of PR/commit #99

Commit/PR #99 (`Execution bridge: evaluated NOM and Slim ontladen winners`) was created on 2026-08-12 **during the ADR recovery work**. It must therefore not be described as old Price Driven v1 legacy code.

#99 did two different things in the same recovery step:

- it removed the legacy Price Driven v1 runtime options and routed the live runtime exclusively through the canonical price pipeline;
- it introduced `LiveModeControl` as a deliberately narrow execution bridge for the then-available evaluated NOM and Slim-ontladen winners.

At that moment the bridge allowed live/dry-run validation to continue before the full accepted Execution chain was connected. Later work, especially ADR-043, ADR-044 and ADR-045, extended the canonical planning pipeline beyond what that narrow bridge can represent.

The correct interpretation is therefore:

- Price Driven v1 is legacy and must stay removed;
- `LiveModeControl` is **transitional recovery code**, not the intended final architecture;
- its valid behaviour must not simply be deleted before the accepted Execution chain reproduces it;
- it must not be extended into the permanent route for ADR-044 timed charging or future primitives.

## Current runtime gap

The main remaining architectural gap is between live Evaluation and the existing Execution architecture.

The current live ADR-037 readiness path runs the real planner pipeline and obtains a real planning result, including the Evaluation Result and Winning Energy Path, but then reduces that result to dashboard/log fields. The rich domain object is not yet carried forward into `ExecutionPlanBuilder` and `ExecutionEngine`.

Separately, the transitional `LiveModeControl` currently infers certain @gielz/Zendure modes from patterns in a winning candidate identifier. This is the narrow bridge introduced by #99. It is allowed to exist only while its behaviour is being migrated to the accepted execution architecture.

In particular, future timed charging must not be implemented as:

`candidate_id -> vendor mode`

The restored architecture must be:

`EvaluationResult -> ExecutionPlanSet -> ExecutionEngine -> ExecutionPrimitiveRequest -> Device Adapter -> @gielz/Zendure command`

## Responsibility migration for LiveModeControl

The current bridge combines responsibilities that belong to separate architectural layers. During replacement, its behaviour is distributed as follows:

- **Planner / Candidate Generation**: produces explicit Energy Path segments with generic `ExecutionPrimitive`, timing and requested power where applicable. It does not choose vendor mode strings.
- **ExecutionPlanBuilder**: converts the Winning Energy Path to `ExecutionPlanSet` without reinterpreting candidate identifiers or planner intent.
- **ExecutionEngine**: determines due segments and validates execution against timing, capabilities and current state before producing an `ExecutionPrimitiveRequest`.
- **Device Adapter**: translates the validated generic primitive into the concrete @gielz/Zendure control semantics, including mode-selector values where appropriate.
- **Dispatcher**: performs only the already-translated Home Assistant dispatch and does not contain planner policy.
- **Runtime composition**: connects the layers and records evidence; it does not make energy-strategy or vendor-control decisions itself.

The capability support added by #99, including `BALANCE_DISCHARGE_ONLY`, remains valid capability information and is not removed merely because `LiveModeControl` is transitional.

## ADR-044 timed acquisition status

ADR-044 can already produce timed Energy Path segments when additional acquisition is required. Those segments contain the generic execution intent, including timing and requested power where applicable.

The next task is therefore not to invent another candidate type or bypass execution validation. The next task is to carry the evaluated winner through the accepted execution contracts.

Temporary architecture bridges must be visible and traceable. They may never rely only on developer memory or chat history.

- **Status:** ACTIVE — replacement planned
- **Introduced:** #99, 2026-08-12
- **Reason:** narrow bridge to dispatch evaluated NOM and Slim-ontladen winners while the canonical planner recovery was ahead of the full live Execution-chain integration.
- **Temporary scope:** candidate-ID recognition, mapping of those recognised winners to generic primitives/vendor mode requests, duplicate-request suppression and bridge-level dispatch evidence.
- **Must not be extended for:** ADR-044 timed charging, new candidate families, new execution primitives or general planner-to-device routing.
- **Replacement path:** `EvaluationResult -> ExecutionPlanSet -> ExecutionEngine -> ExecutionPrimitiveRequest -> Device Adapter -> @gielz/Zendure dispatch`.
- **Removal criteria:** the accepted Execution path reproduces the valid NOM and Slim-ontladen behaviour of #99 in dry-run; ADR-044 timed execution travels through the same path; tests prove no candidate-ID-to-vendor-command dependency remains; runtime no longer imports or calls `LiveModeControl`.
- **Removal action:** delete `LiveModeControl` and its bridge-specific tests rather than keeping an inactive compatibility implementation.

## Project rule for all future temporary code

Any future bridge, shim, compatibility route or deliberately temporary architectural code must be marked **at the code location where it exists** and tracked in the development log.

The code marker must state at minimum:

- that the code is temporary;
- why it exists;
- which responsibility or architectural boundary it temporarily bridges;
- which accepted ADR(s) define the intended permanent route;
- a reference to its Temporary Architecture Bridge log entry;
- the concrete condition under which it must be removed.

The development log entry must use a stable identifier (`TAB-xxx`) and record status, introduction point, temporary scope, forbidden extension scope, replacement path and removal criteria.

A temporary bridge is not allowed to become permanent merely because it works. If its replacement reveals an architectural gap or ADR conflict, implementation stops and the design process is resumed instead of extending the bridge.

## Rules for all work from this point

The following rules apply to the recovery work:

- Accepted ADRs are frozen architectural records.
- Do not edit an accepted ADR merely to match existing code.
- When an ADR is genuinely incomplete or conflicts with another accepted ADR, create a new ADR describing the missing decision or resolution.
- Do not implement architectural policy hidden inside runtime conditionals, candidate-ID parsing, adapter exceptions or one-off device hacks.
- Do not treat existing live configuration or legacy/transitional runtime code as architectural authority.
- Do not create a workaround just to make live control happen sooner.
- Keep dry-run/observer operation as the safe default while restoring the execution chain.
- Before enabling live control, prove the complete traceability chain from planning evidence to execution request and adapter dispatch.
- If the accepted architecture cannot be implemented cleanly, stop implementation and return to design review.

## Agreed replacement sequence

The replacement of TAB-001 proceeds in this order:

1. Preserve the real ADR-037 planning/evaluation domain result after evaluation instead of reducing the only usable result to dashboard/log fields.
2. Hand the winning `EvaluationResult` to the existing ADR-033 `ExecutionPlanBuilder`.
3. Connect the resulting `ExecutionPlanSet` to the existing `ExecutionEngine` using the live capability/current-state evidence required by the accepted contracts.
4. Route validated `ExecutionPrimitiveRequest` objects through the Device Adapter boundary to the existing @gielz/Zendure device-facing control interface.
5. In dry-run, prove that `BALANCE_BIDIRECTIONAL` and `BALANCE_DISCHARGE_ONLY` reproduce the valid NOM/Slim-ontladen behaviour currently provided by #99.
6. Prove that ADR-044 timed execution uses the same architecture without a special runtime shortcut.
7. Remove `LiveModeControl`, its runtime call path and bridge-specific tests.
8. Perform a repository-wide audit for remaining Price Driven v1 runtime traces, candidate-ID command parsing, direct planner/device dispatch and other parallel execution routes. Historical documentation remains intact.

No step may be skipped by enabling `control_change_allowed` or by adding another direct dispatch shortcut.

### Step 1 — preserve typed planner result

The live ADR-037 runtime now preserves the typed `ADR037PlanningResult` from the same planner pass that produces readiness/dashboard evidence. ### Step 2 — EvaluationResult to ADR-033 ExecutionPlanBuilder

**Status:** PAUSED FOR ARCHITECTURE — no workaround implemented

At the start of step 2, review of the accepted execution contracts found a genuine missing contract. ADR-033 requires `ExecutionPlanBuilder` to receive an explicit non-empty `fallback_policy_id` and forbids the builder from selecting or inventing one. ADR-016 requires Execution Plan validation to verify fallback availability. The repository currently contains no canonical fallback-policy record, registry, runtime selection rule or live configured policy identity.

Supplying an arbitrary string such as `default` would satisfy the current type signature but would create hidden architecture in runtime code and make fallback availability impossible to validate meaningfully. In accordance with the recovery rules, implementation therefore stopped before wiring the builder.

A new architecture proposal has been created as **ADR-046 — Execution Fallback Policy Registry and Selection** in PR #119. It proposes a vendor-independent canonical policy `execution-fallback:hold-and-replan:v1`, an immutable policy registry and explicit runtime composition input. ADR-046 remains **Proposed** until explicitly accepted; no accepted ADR or runtime code was changed as part of this finding.

Step 2 resumes only after the fallback-policy contract is accepted or otherwise resolved architecturally.
